Headless mode runs Grok non-interactively from the command line. It accepts a single prompt, executes it with full tool access, and prints the result to stdout. Use it to automate tasks, script workflows, build integrations, and parse output programmatically. The process exits when the response is complete.

## Basic Usage

Passing a prompt non-interactively triggers headless mode. The most common way is the `-p` flag (short for `--single`):

```bash
grok -p "Your prompt here"
```

You can also supply the prompt as a JSON content block or from a file:

```bash
# JSON prompt
grok --prompt-json '{"type":"text","text":"Explain this codebase"}'

# Prompt from a file
grok --prompt-file ./prompt.txt
```

Grok processes the prompt, runs any necessary tools, and prints the result to stdout.

## Output Formats

Headless mode supports four output formats, selected with `--output-format`:

| Format | Flag | Description |
| --- | --- | --- |
| `plain` | *(default)* | Human-readable text, suitable for direct display or piping |
| `json` | `--output-format json` | Single JSON object emitted after the response completes, containing `text`, `stopReason`, `sessionId`, `requestId`, and token usage fields |
| `streaming-json` | `--output-format streaming-json` | Newline-delimited JSON (NDJSON) event stream; one `type`-tagged object per line |
| `streaming-messages-json` | `--output-format streaming-messages-json` | NDJSON in the Messages API wire format with `assistant`/`user` message bodies |

### plain (default)

Human-readable text output:

```
Here's a summary of the codebase...
```

### json

A single JSON object emitted after the response completes. Includes response text, stop reason, session ID, request ID, and token usage when available:

```json
{
  "text": "Here's a summary of the codebase...",
  "stopReason": "end_turn",
  "sessionId": "abc123",
  "requestId": "xyz789",
  "num_turns": 7,
  "usage": {
    "input_tokens": 7210,
    "cache_read_input_tokens": 41000,
    "cache_creation_input_tokens": 0,
    "output_tokens": 1893,
    "total_tokens": 50103
  },
  "total_cost_usd": 0.01268905
}
```

The `sessionId` field is useful for resuming the conversation in a later call.

### streaming-json

Newline-delimited JSON with one `type`-tagged event per line:

```json
{"type":"thought","data":"Analyzing the directory structure..."}
{"type":"tool_call","toolCallId":"call_1","title":"Read","toolName":"read_file","status":"in_progress","rawInput":{"path":"src/main.rs"},"content":[],"locations":[]}
{"type":"tool_call_update","toolCallId":"call_1","status":"completed","rawOutput":{"lines":42},"content":[],"locations":[]}
{"type":"text","data":"Here's a summary"}
{"type":"end","stopReason":"end_turn","sessionId":"abc123","requestId":"xyz789"}
```

| Event Type | Description |
| --- | --- |
| `text` | A chunk of the agent's response text |
| `thought` | Internal reasoning (thinking tokens) |
| `tool_call` | A tool call the agent started |
| `tool_call_update` | Progress or result for an in-flight tool call |
| `usage` | Per-response boundary with token counts |
| `plan` | The agent's current plan |
| `end` | Final event with metadata and spend fields |
| `error` | An error occurred |

### streaming-messages-json

NDJSON in the Messages API wire format. Useful for consumers that already parse Messages API streaming responses:

```json
{"type":"system","subtype":"init","session_id":"abc123","model":"grok-build","cwd":"/repo","tools":["read_file","bash"]}
{"type":"assistant","message":{"role":"assistant","content":[{"type":"text","text":"Let me read the file."}],"stop_reason":"tool_use"}}
{"type":"result","subtype":"success","result":"Here's a summary...","stop_reason":"end_turn","total_cost_usd":0.0127}
```

## CI/CD Integration

### Automated Code Review

```bash
grok -p "Review changes for bugs and security issues." \
  --output-format json --yolo | jq -r '.text' > review.md
```

### GitHub Actions Workflow

```yaml
name: AI Code Review
on: [pull_request]

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install Grok Build
        run: curl -fsSL https://grok.build/install.sh | sh

      - name: Run AI review
        env:
          XAI_API_KEY: ${{ secrets.XAI_API_KEY }}
        run: |
          grok -p "Review the staged changes for bugs and security issues." \
            --output-format json --yolo | jq -r '.text' > review.md

      - name: Upload review
        uses: actions/upload-artifact@v4
        with:
          name: ai-review
          path: review.md
```

### Environment Variable Setup

For CI environments without browser access, set your API key from [console.x.ai](https://console.x.ai):

```bash
export XAI_API_KEY="xai-..."
grok -p "Run the test suite" --yolo
```

Key environment variables:

| Variable | Description |
| --- | --- |
| `XAI_API_KEY` | API key for authentication (required when no browser login) |
| `GROK_HOME` | Override config directory (default: `~/.grok`) |
| `GROK_LOG_FILE` | Path to a log file (works in headless and TUI, honors `RUST_LOG`) |
| `RUST_LOG` | Log level filter (e.g. `debug`). Headless logs go to stderr. |

## Session Management in Headless Mode

By default, each `grok -p` invocation creates a fresh session. To maintain context across calls, use session flags.

### Resume an existing session (`-r`)

The `-r` / `--resume` flag resumes a session by ID, or by title for the current directory (case-insensitive). It errors if the session does not exist:

```bash
# Resume by session ID
grok -p "What's the secret number?" --resume abc123

# Resume by title (for the current directory)
grok -p "Continue the refactor" --resume "my-feature"
```

### Continue most recent session (`-c`)

The `-c` / `--continue` flag continues the most recent session in the current working directory:

```bash
grok -p "Continue where we left off" -c
```

### Create session with specific UUID (`-s`)

Use `-s` / `--session-id` only to **create** a new session with a client-chosen UUID. It does not resume—use `-r` or `-c` for that:

```bash
grok -p "hello" --session-id "$(uuidgen | tr '[:upper:]' '[:lower:]')" --output-format json
```

### Fork session history (`--fork-session`)

When combined with `-r` or `-c`, `--fork-session` branches the history into a new session instead of appending to the original:

```bash
grok -p "Try a different approach" --resume abc123 --fork-session
```

### Capture session ID for later use

```bash
SESSION=$(grok -p "Hello" --output-format json | jq -r '.sessionId')
grok -p "Follow-up question" --resume "$SESSION"
```

## Common Flags

| Flag | Description |
| --- | --- |
| `-p, --single <PROMPT>` | The prompt text to send |
| `--prompt-json <JSON>` | Prompt as JSON content blocks |
| `--prompt-file <PATH>` | Read prompt from a file |
| `-r, --resume <ID_OR_TITLE>` | Resume an existing session by ID or title |
| `-c, --continue` | Continue the most recent session in the current directory |
| `-s, --session-id <UUID>` | Create a new session with a specific UUID (does not resume) |
| `--fork-session` | With `-r`/`-c`, fork history into a new session |
| `--output-format <FMT>` | Output format: `plain`, `json`, `streaming-json`, `streaming-messages-json` |
| `--yolo` | Auto-approve all tool executions |
| `-m, --model <MODEL>` | Model to use (e.g. `grok-build`) |
| `--cwd <PATH>` | Set the working directory |
| `--rules <TEXT>` | Inline project rules appended to the system prompt |
| `--tools <TOOLS>` | Allowlist of built-in tools (comma-separated, headless only) |
| `--disallowed-tools <TOOLS>` | Denylist of built-in tools to remove (comma-separated, headless only) |
| `--max-turns <N>` | Maximum number of agentic turns before stopping (headless only) |
| `--permission-mode <MODE>` | Permission mode (e.g. `bypassPermissions`) |
| `--allow <RULE>` | Permission allow rule with glob patterns (repeatable) |
| `--deny <RULE>` | Permission deny rule with glob patterns (repeatable) |
| `--no-auto-update` | Disable update checks for this session |

## Exit Codes

| Code | Meaning |
| --- | --- |
| `0` | Success — the prompt completed normally |
| `1` | Error — authentication failure, network error, or runtime error |
| `130` | Interrupted by SIGINT (Ctrl+C) |
| `143` | Terminated by SIGTERM |

On SIGINT or SIGTERM, session state is saved up to the last completed tool call. File modifications by tools are **not** rolled back. Resume an interrupted run with `grok -p "continue" --resume "<id>"`.

## Debug Logging

Raise the log level with `RUST_LOG` and redirect stderr to capture diagnostics:

```bash
RUST_LOG=debug grok -p "Your prompt here" 2> debug.log
```

Update messages and diagnostic output go to **stderr**. Stdout stays clean for `--output-format json`.

<Warning>
`--yolo` (alias `--always-approve`) disables interactive permission prompts so all tool executions run without confirmation. Deny rules, hooks, and admin locks still apply. Use with care in CI — combine it with `--rules` to set guardrails: `grok -p "..." --yolo --rules "Never delete files"`.
</Warning>
