Agent mode runs Grok as a long-lived server that clients communicate with over [ACP](https://agentclientprotocol.com) (Agent Client Protocol), a JSON-RPC 2.0 protocol. Clients — IDEs, SDKs, eval harnesses, and custom apps — connect to the running agent, create sessions, send prompts, and receive streaming updates. The agent process stays alive between requests, so session state and MCP connections persist across turns.

<Note>
For one-shot prompts that print output and exit, use `grok -p` ([headless mode](/headless-mode)) instead. Agent mode is designed for long-lived, programmatic integrations.
</Note>

---

## When to Use Agent Mode

| Use case | Recommended approach |
| --- | --- |
| One-shot script or CI step | `grok -p` (headless mode) |
| IDE or editor extension | `grok agent stdio` |
| SDK or eval harness | `grok agent stdio` or `grok agent serve` |
| Multi-turn automation | `grok agent stdio` |
| Remote / browser-based client | `grok agent serve` with WebSocket |

## Starting Agent Mode

### stdio (local process)

The stdio transport is the standard path for local integrations. The agent reads JSON-RPC from stdin and writes responses to stdout:

```bash
# stdio (local process / many SDKs)
grok agent --always-approve stdio
```

### WebSocket server

To accept remote connections, start a WebSocket server. Clients authenticate with the secret token:

```bash
# WebSocket server
grok agent --always-approve serve --bind 127.0.0.1:2419 --secret <token>
```

If you omit `--secret`, the agent prints a generated token at startup. You can also set `GROK_AGENT_SECRET` in the environment.

### Agent mode flags

Agent options go after `agent` and before the mode name. Mode-specific flags (e.g. `--bind`) go after the mode:

```bash
grok agent --always-approve --model grok-build stdio
grok agent --always-approve serve --bind 127.0.0.1:2419 --secret <token>
```

| Flag | Description |
| --- | --- |
| `--always-approve` / `--yolo` | Run without interactive tool-permission prompts |
| `--reauth` | Authenticate before the agent starts |
| `--leader` / `--no-leader` | Connect to a shared leader process (`--leader`), or force a fresh standalone agent (`--no-leader`). When a non-`off` sandbox profile is requested, leader mode is refused automatically so tools stay in-process |
| `--plugin-dir <PATH>` | Load plugins from a directory (repeatable); plugins are auto-trusted |
| `--bind <HOST:PORT>` | Bind address for `serve` mode (default: `127.0.0.1:2419`) |
| `--secret <TOKEN>` | Authentication token for WebSocket clients |
| `-m, --model <MODEL>` | Model ID (e.g. `grok-build`) |
| `--agent-profile <PATH>` | Load an agent profile from a file |

## ACP Protocol Overview

Communication follows [JSON-RPC 2.0](https://www.jsonrpc.org/specification). A typical session lifecycle:

1. **Initialize** — client sends `initialize` with its capabilities
2. **Create session** — client sends `session/new` with working directory and MCP server config
3. **Send prompts** — client sends `session/prompt` with user messages
4. **Receive updates** — agent sends `session/update` notifications with streamed content
5. **Handle permissions** — agent may request tool-execution approval (unless `--always-approve`)

```text
+------------------------------------------+
|           ACP Client                     |
|  (IDE, Editor, Custom Application)       |
+-------------------+----------------------+
                    | JSON-RPC over stdio
+-------------------v----------------------+
|           grok agent stdio               |
|                                          |
|  +---------+  +---------+  +---------+   |
|  | Session |  |  Tools  |  |   MCP   |   |
|  | Manager |  | Registry|  | Servers |   |
|  +---------+  +---------+  +---------+   |
+------------------------------------------+
```

### Streaming updates

Each `session/update` notification carries a `sessionUpdate` field:

| `sessionUpdate` value | Description |
| --- | --- |
| `agent_message_chunk` | A chunk of the agent's response text |
| `agent_thought_chunk` | A chunk of the agent's internal reasoning |
| `tool_call` | A new tool invocation (title, kind, status, input) |
| `tool_call_update` | A status or result update for an in-flight tool call |
| `plan` | The agent's current execution plan |

### Extension methods

Beyond the base ACP protocol, Grok defines extension methods under the `x.ai/` prefix:

| Category | Prefix | Examples |
| --- | --- | --- |
| Filesystem | `x.ai/fs/*` | `list`, `exists`, `read_file`, `write_file` |
| Git | `x.ai/git/*` | `status`, `stage`, `commit`, `diffs`, `discard` |
| Git Worktree | `x.ai/git/worktree/*` | `create`, `remove`, `apply`, `list`, `gc` |
| Search | `x.ai/search/*` | `fuzzy/open`, `fuzzy/change`, `content` |
| Terminal | `x.ai/terminal/*` | `create`, `kill`, `output`, `wait_for_exit` |
| Session Management | `x.ai/session/*` | `fork`, `resolve_local_for_worktree_resume` |
| Conversation | `x.ai/*` | `prompt_history`, `rewind/*`, `compact_conversation` |
| Authentication | `x.ai/auth/*` | `get_url`, `submit_code` |
| Feedback & Telemetry | `x.ai/*` | `feedback`, `telemetry/*` |

The `x.ai/*` set is SpaceXAI-specific and may expand across releases. Discover available methods from the agent's `initialize` response.

## Session Management via ACP

Sessions are created and loaded via protocol methods:

```typescript
// Create new session
const { sessionId } = await connection.request("session/new", {
  cwd: "/path/to/project",
  mcpServers: [],
});

// Load existing session
await connection.request("session/load", {
  sessionId: "existing-session-id",
  cwd: "/path/to/project",
  mcpServers: [],
});
```

### Session `_meta` options

Optional fields on `session/new`:

| Field | Description |
| --- | --- |
| `rules` | Extra rules appended to the system prompt |
| `systemPromptOverride` | Replacement system prompt |
| `agentProfile` | Agent profile name or JSON object |
| `yoloMode` | When `true`, always-approve for this session |
| `autoMode` | When `true`, auto permission mode for this session |

```json
{
  "cwd": "/path/to/project",
  "mcpServers": [],
  "_meta": { "yoloMode": true }
}
```

## Sending Turns

Send a prompt to an active session with `session/prompt`:

```typescript
const msg = JSON.stringify({
  jsonrpc: "2.0",
  id: 1,
  method: "session/prompt",
  params: {
    sessionId: sessionId,
    prompt: [{ type: "text", text: "List the files in this project" }],
  },
});
process.stdin.write(msg + "\n");
```

The agent streams `session/update` notifications back. Each notification's `params.update` object has a `sessionUpdate` field identifying the event type. The turn ends when you receive a final result response.

## TypeScript Integration Example

```typescript
import { spawn, ChildProcess } from "child_process";
import * as readline from "readline";

class GrokACPChat {
  private proc!: ChildProcess;
  private sessionId!: string;
  private rl!: readline.Interface;

  constructor(private cwd = ".") {}

  async init() {
    this.proc = spawn("grok", ["agent", "--always-approve", "stdio"]);
    this.rl = readline.createInterface({ input: this.proc.stdout! });

    await this.request("initialize", {
      protocolVersion: 1,
      clientCapabilities: {
        fs: { readTextFile: true, writeTextFile: true },
        terminal: true,
      },
    });

    const { sessionId } = await this.request("session/new", {
      cwd: this.cwd,
      mcpServers: [],
      _meta: { yoloMode: true },
    });
    this.sessionId = sessionId;
    return this;
  }

  private async request(method: string, params: any): Promise<any> {
    return new Promise((resolve) => {
      const msg = JSON.stringify({ jsonrpc: "2.0", id: 1, method, params });
      this.proc.stdin!.write(msg + "\n");

      this.rl.once("line", (line) => {
        resolve(JSON.parse(line).result || {});
      });
    });
  }

  async *streamPrompt(text: string) {
    const msg = JSON.stringify({
      jsonrpc: "2.0",
      id: 1,
      method: "session/prompt",
      params: {
        sessionId: this.sessionId,
        prompt: [{ type: "text", text }],
      },
    });
    this.proc.stdin!.write(msg + "\n");

    for await (const line of this.rl) {
      const data = JSON.parse(line);

      if (data.method === "session/update") {
        const update = data.params.update;
        yield update; // { sessionUpdate, content, title, ... }
      } else if (data.result) {
        break; // Final response
      }
    }
  }
}

// Usage
const client = await new GrokACPChat(".").init();

for await (const update of client.streamPrompt("List the files in this project")) {
  switch (update.sessionUpdate) {
    case "agent_message_chunk":
      process.stdout.write(update.content?.text || "");
      break;
    case "agent_thought_chunk":
      console.log(`\n[Thinking: ${update.content?.text}]`);
      break;
    case "tool_call":
      console.log(`\n[Tool: ${update.title}]`);
      break;
  }
}
```

## Plugin Directory

The `--plugin-dir` flag (repeatable) loads plugins from a directory for the running agent process. Plugins loaded this way are automatically trusted — no interactive confirmation is required:

```bash
grok agent --always-approve --plugin-dir ./my-plugins stdio
```

This is useful for CI or SDK scenarios where you bundle specific MCP servers or tool definitions alongside the agent process.

---

## Leader Mode

By default, Grok can connect multiple client sessions to a single shared **leader process** to reduce startup overhead and share MCP connections. Configure this in your `config.toml`:

```toml
[cli]
use_leader = true
```

Use `--no-leader` to force a fresh, standalone agent process instead of connecting to the shared leader. Note: when a non-`off` sandbox profile is requested, leader mode is automatically refused so tools stay in-process.
